Two computers, one conversation

Loading a page is this conversation, every time — the question is always where each step runs and when.

Primer · optional

What "rendering" means

Two open questions every framework has to answer: where does this happen (browser or server)? when (once, ahead of time — or fresh, every visit)?

Primer · optional

Build time vs. runtime

What triggers build time?A developer (or a CI/CD pipeline) running next build — normally as part of shipping a new deploy. It fires once per deploy, for everyone, not once per visitor.
What triggers runtime?A real visitor doing something — their browser loading the page (always true for anything client-side), or, only if there's a live server behind the app, their request hitting that server fresh.
Does this always happen?Not necessarily both. Some apps have no live server at all once deployed — in that case "runtime" only ever means "in the visitor's browser," and whatever ran at build time never runs again for anyone. We'll see exactly where that applies later in Part 1.
Presenter note The key thing this diagram adds: build doesn't just "run the code once" — it splits it into two different compiled outputs, one that ships to the browser and one that stays on the server. Everything left of the dashed line happens exactly once, no matter how many visitors show up. Everything right of it — client → server → client — is the SAME three-step handshake repeating for every single visit. CSR/SSR/SSG/RSC, coming up next, are really just different answers to "how much of that right-hand loop actually touches the server?"

Part One

FE Rendering
Strategies

Four ways to answer one question: where + when does this page get built?

  • CSR — Client-Side Rendering
  • SSR — Server-Side Rendering
  • SSG — Static Site Generation
  • RSC — React Server Components
CSR · process

Client-Side Rendering

Presenter note There are TWO separate round trips, not one — walk them explicitly. The first only fetches code (shell + JS bundle); nothing meaningful is on screen yet. Only once that JS has run does the SECOND trip happen, to fetch actual data. Good live question: "why can't the browser ask for the shell and the data at the same time?" — because it doesn't know what data it needs until the JS defining that need has already executed.
CSR · example

What it looks like

function Dashboard() {
  const [data, setData] = useState(null);
  useEffect(() => {
    fetch('/api/stats')
      .then(r => r.json())
      .then(setData);
  }, []);
  return data ? <Chart data={data}/> : <Spinner/>;
}
Real-world caseClassic SPAs (create-react-app era), internal admin dashboards, Gmail-style apps — SEO usually doesn't matter.
Ask the roomWhere exactly does the loading spinner sit in the flowchart we just drew? Chat it.
Code walkthrough useState(null) starts with no data at all. useEffect(..., []) — empty dependency array — runs exactly once, right after this component first mounts IN THE BROWSER; that's the moment round trip #2 fires. Until setData resolves, the component returns <Spinner/>; once it resolves, it re-renders with <Chart/>. Nothing here could run on a server at all — there's no DOM, no DOM to attach the spinner to, until a browser exists.

Answer to "ask the room" The spinner lives in the gap between "browser parses JS" and "sends JSON data" — during the SECOND round trip, not the first. During round trip #1 (getting the shell + bundle) there's typically nothing rendered at all — a blank page. The spinner only appears once enough JS has run to render a loading state while it waits on the data fetch.
SSR · process

Server-Side Rendering

Presenter note Say the caption out loud: "happens again, every single request." Contrast directly with SSG two slides from now — the diagrams look almost identical except WHEN that server work happens. Also flag: hydration still has to finish before anything is clickable, even though the HTML arrived instantly — the visitor sees content right away but can't interact with it yet.
SSR · example

What it looks like

Pages Router syntax App Router does this differently — see Part 1's RSC section
export async function getServerSideProps({ params }) {
  const product = await db.getProduct(params.id);
  return { props: { product } };
}
export default function ProductPage({ product }) {
  return <ProductView product={product}/>;
}
Real-world caseAmazon-style product pages — price/stock can't be stale, so it's recomputed on every visit.
Ask the roomIf the server is slow right now, what does the visitor experience that CSR's visitor wouldn't? Chat it.
Code walkthrough getServerSideProps is a specially-named export Next.js looks for — if present, it's called ON THE SERVER, for every request, BEFORE the page component ever runs. params.id comes straight from the URL (e.g. /products/42). Whatever it returns under props gets handed directly to ProductPage — by the time that component runs, product is already real data, so there's no loading state to write.

Answer to "ask the room" In SSR, everything waits on the server — the visitor sees a blank tab until the server finishes running code, fetching data, AND building HTML, because nothing is sent down until all of that is done. In CSR, the empty shell + JS bundle usually arrive fast (they're static), so the visitor sees a spinner or skeleton almost immediately even if the data fetch is slow. SSR trades that early "something's happening" feedback for one clean round trip.
SSG · process

Static Site Generation

Presenter note This is the live payoff of the build-time-vs-runtime primer — point back to that slide explicitly. The dashed divider is real: there's an actual gap in time (minutes, or months) between the build-machine steps and the first visitor. The CDN step is deliberately drawn in neutral gray, not teal — nothing is "running" at that point, a file is just being handed over, which is why SSG hosting is so cheap compared to SSR.
SSG · example

What it looks like

Pages Router syntax App Router does this differently — see Part 1's RSC section
export async function getStaticProps({ params }) {
  const post = await cms.getPost(params.slug);
  return { props: { post } };
}
export async function getStaticPaths() {
  const slugs = await cms.listSlugs();
  return {
    paths: slugs.map(slug => ({ params: { slug } })),
    fallback: false,
  };
}
Real-world caseDocs sites, marketing blogs — built once, served from a CDN forever, until the next deploy.
Ask the roomWhat's the actual tradeoff vs. SSR here — what do you give up to get that speed? Chat it.
Code walkthrough This looks almost identical to the SSR snippet two slides back — same shape, different TIMING, which is the whole point. getStaticPaths answers "which slugs exist?" ahead of time so Next.js knows every page to pre-build; fallback: false means any slug not in that list 404s rather than being built on demand. getStaticProps then runs once per slug, at build time, not per visitor.

Answer to "ask the room" Freshness. SSG's HTML was correct as of whenever next build last ran — if the underlying data changes (a price, a typo fix, new content), visitors keep seeing the OLD version until the next build and deploy. SSR recomputes on every request, so it's always current, at the cost of per-request server compute and slower responses under load.

RSC · process

React Server Components

The decision moves from per page to per component, inside the same tree.

Presenter note The left box has no internal color on purpose — in the old model you couldn't mix strategies within one page, so there was nothing to color-differentiate. The right box's dashed OUTER boundary represents "still one page"; the colors INSIDE it are what's new. If someone asks "doesn't SSR also run on the server first?" — yes, the difference isn't server-vs-client in isolation, it's that the choice now happens per component instead of per page.

Part Two · setting the stage

What exactly is "the App Router"?

In one lineIt's Next.js's routing system, built around the app/ directory — the concrete, shippable implementation of the Server/Client tree you just saw in Part 1.
Pages Router (old)App Router (new)
Directorypages/app/
Routing unitOne file = one pageA nested tree: page.tsx, layout.tsx, loading.tsx, error.tsx
Rendering decisionThe whole page picks one strategyEach component picks Server or Client
CallbackThat "App Router / RSC" tree from Part 1 — teal and amber nodes inside one dashed page boundary? That tree is the App Router. app/ is just Next.js's name for "a directory where this per-component choice is real, not theoretical."

Everything in Part 2 — the primitives, the pages, every 'use client' — lives inside this app/ structure in the real codebase.

2.1 · example

No directive needed

Server-safe button.tsx
const buttonVariants = cva(
  'inline-flex items-center justify-center gap-2 rounded-md text-sm font-medium …',
  {
    variants: {
      variant: { default: '…', brand: '…', destructive: '…', outline: '…', ghost: '…' },
      size: { default: 'h-9 px-4 py-2', sm: '…', lg: '…', icon: '…' },
    },
  },
);
Code walkthrough cva ("class-variance-authority") isn't React-specific — it's a plain function that takes a BASE set of classes (always applied) plus a variants map, and hands back a function. Calling buttonVariants({ variant: 'brand', size: 'sm' }) returns the final className string for that combination — pure string logic, nothing else. No hooks, no DOM, no browser API in sight, which is exactly why this file needs no 'use client' — it would produce the identical output whether Node or a browser evaluated it.
2.1 · example

Radix needs the browser

Client component modal.tsx
'use client';
import * as DialogPrimitive from '@radix-ui/react-dialog';

const Modal = DialogPrimitive.Root;

function ModalOverlay({ className, ref, ...props }) {
  return (
    <DialogPrimitive.Overlay
      ref={ref}
      className={cn('fixed inset-0 z-40 bg-black/20 …', className)}
      {...props}
    />
  );
}
What is Radix? An unstyled, accessible component library (Dialog, Dropdown, Tooltip, Tabs…) — it handles focus-trapping inside an open dialog, returning focus on close, Escape/outside-click, ARIA attributes, and portaling to the end of <body>. It ships zero CSS on purpose.

Code walkthrough Modal is DialogPrimitive.Root re-exported with NO wrapping at all — it's pure state/behavior, nothing to style. ModalOverlay exists only to add Tailwind classes via cn(...) on top of Radix's unstyled Overlay part. All of Radix's focus-trap/portal/keyboard logic needs useRef/useState internally — that's the hard, mechanical reason this file requires 'use client', not a style preference.
Key insight

You pay for client JS per primitive, not per page

2.2

Composition: the thin-orchestrator chain

2.2 · in plain terms

Think of it like ordering delivery

RestaurantCode layerRole
Host / managerPageDecides what you're seeing right now, coordinates the visit
Your waiterCompositeHandles one specific request directly — refills, the check
The order ticket formatHookA consistent way to write down "what's needed"
The delivery runnerAPI clientPhysically carries the request and brings the result back
The kitchenBackendDoes the real work — cooks the food

Keep this mapping in mind — we'll walk through each layer one at a time next.

2.2 · layer 1 of 4

The Page — like the host

In the restaurantThe host seats you and decides what you see next — but doesn't personally take your order or cook anything.
In the codeHolds route-level UI state (which filter/tab is active) and composes everything else together. It doesn't own data mutations itself.
2.2 · layer 2 of 4

The Composite — like your waiter

In the restaurantYour waiter handles one specific interaction directly — taking an order, bringing the check — without you talking straight to the kitchen.
In the codeReceives data via props from the page, but owns and calls its own mutation hooks directly — it doesn't bubble the action back up.
2.2 · layer 3 of 4

The Hook — like the order ticket

In the restaurantA standard ticket format the kitchen expects — any waiter can fill one out and the kitchen knows exactly how to read it.
In the codeWraps the request in React Query (useQuery / useMutation) — consistent caching, loading, and retry behavior everywhere it's used.
2.2 · layer 4 of 4

The API client — like the delivery runner

In the restaurantPhysically carries the ticket to the kitchen and brings the finished dish back. Doesn't decide what's ordered — just transports it.
In the codeA typed fetch wrapper that makes the actual HTTP call — e.g. userApiClient.listByStatus(...) — talking to the backend (the kitchen).
2.2 · in action · 1 of 4

The Page, in action

Example process:

  1. Visitor opens /users
  2. UsersPage mounts, status initializes to 'ACTIVE'
  3. Calls useUsersByStatus(status)
  4. Renders <UsersTable users={data}/> once data resolves
2.2 · in action · 2 of 4

The Composite, in action

Example process:

  1. UsersTable renders one <UserActions user={row}/> per row
  2. You click "Activate" on Jordan Ellis's row
  3. UserActions calls its OWN hook: useActivateUser().mutate(user.userId)
  4. The page never even knows this happened — no prop, no callback, no page-level state change
2.2 · in action · 3 of 4

The Hook, in action

Example process:

  1. useActivateUser() is called inside UserActions
  2. Internally wraps React Query's useMutation — tracks loading/error/success
  3. On .mutate(...), calls the API client and manages cache invalidation
  4. The same hook could be called from a totally different component tomorrow and behave identically
2.2 · in action · 4 of 4

The API client, in action

Example process:

  1. The hook's mutation function calls userApiClient.activate(userId)
  2. That function does the literal fetch(...) with method: 'POST'
  3. The browser sends a real HTTP request across the network to the backend
  4. The response comes back, the hook updates its cache, React re-renders
2.2 · example

Which layer owns the mutation?

export default function UsersPage() {
  const [status, setStatus] = useState('ACTIVE');
  const { data } = useUsersByStatus({ userStatus: status });
  return <UsersTable users={data?.data}/>;
}

export function UserActions({ user }) {
  const activateUser = useActivateUser();
  return <Button onClick={() => activateUser.mutate(user.userId)}>Activate</Button>;
}

Code walkthrough UsersPage holds exactly one piece of state (status) and calls ONE hook — useUsersByStatus — to fetch a LIST. It never touches user.userId and never calls a mutation; it just hands the fetched list down to <UsersTable> (not shown — it renders one <UserActions user={row}/> per row). This snippet is the literal code proof of "page reads, composite writes."
Answer

The composite — UserActions.

WhyIt reads data via props from its parent, but owns and calls its own mutation hooks directly — it doesn't bubble callbacks all the way up to the page.
Whiteboard

Why use a thin orchestrator?

Compare against what you wrote

Why use a thin orchestrator?

  • Testability — a page with no business logic is trivial to test; the real logic lives in small, focused composites and hooks you can test in isolation.
  • Reuse — the same composite (e.g. UserActions) drops into a table row, a detail page, or a modal, because it owns its own data needs instead of depending on a specific parent to feed it.
  • Change isolation — if the mutation API changes, you edit the composite or hook, not every page that happens to render it.
  • Bundle discipline — keeping pages thin makes the client/server boundary obvious, instead of tempting you to cram unrelated interactivity into the one file that's already 'use client'.
  • Faster onboarding — a new engineer can read any page's ~10 lines and understand the whole screen's shape without reading every component's internals.
Not a new ideaSame shape as "container/presentational" or "smart/dumb components" from years of React practice — this isn't an arbitrary house rule, it's a durable, widely-agreed-on pattern applied consistently.

Closing

Takeaways

  • Rendering is a per-component decision now, not a per-page one.
  • Build time (once, ahead) vs. runtime (live, per visitor) is the axis everything else sits on.
  • "It depends" is often the correct, deliberate answer — not a cop-out.
  • Real component libraries (MUI, shadcn/ui, Radix, @old-st/ui) all make this same split.
